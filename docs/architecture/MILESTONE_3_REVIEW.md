## 2. Deep Security & Hardware Isolation Audit

### 2.1 The DMA Physical Isolation Reality (Critical Security Gap)
#### The Design Claim
`MILESTONE_3_DESIGN.md` states:
> *"A compromised driver could attempt to program a device (e.g. VirtIO disk) to DMA into kernel memory. The capability model prevents this: a driver cannot obtain a physical address for memory it does not own. VirtIO DMA buffers are allocated via `SYS_MAP_FRAME` which verifies ownership."*

#### Hardware Reality & Vulnerability Analysis
This claim represents a **fundamental misunderstanding of PC hardware architecture in the absence of an IOMMU (Intel VT-d / AMD-Vi)**:
1. **CPU MMU vs. Device Bus Master:** The CPU MMU enforces memory protection (Ring 0 vs. Ring 3, supervisor bit, page table permissions) *only* on CPU memory references generated by core instruction fetches and load/store operations.
2. **PCI Bus-Master DMA:** When a PCI device is granted bus mastering (`COMMAND` register bit 2 set), the physical controller emits memory read/write cycles directly onto the PCI/PCIe fabric, translating straight to host physical DRAM via the memory controller.
3. **The Exploit Vector:** Once an untrusted Ring 3 driver possesses an `IOPort` or `MmioFrame` capability to interact with the VirtIO device registers, it directly populates the VirtIO Ring Descriptor Table (`VirtQueue` descriptor entries `addr`, `len`, `flags`). 
4. Even if `SYS_MAP_FRAME` only reveals physical addresses of frames granted to the driver, the driver is running arbitrary code in Ring 3. It can ignore the kernel-provided physical address and write `addr = 0x0000_1000` (the physical address of the kernel PML4 or IDT) directly into the VirtIO descriptor register.
5. When the driver triggers the queue notification (`queue_notify`), the VirtIO controller directly overwrites kernel memory at `0x1000` via physical DMA, completely bypassing the CPU MMU and subverting kernel isolation without ever violating user-space page table permissions.

```
+--------------------------------------------------------------------------+
| Ring 3 Untrusted Driver                                                  |
|   1. Driver allocates valid user frame (paddr 0x4000)                    |
|   2. Malicious driver writes descriptor: addr = 0x1000 (Kernel PML4)     |
|   3. Driver writes queue notify register via MmioFrame/IOPort            |
+--------------------------------------------------------------------------+
                         |
                         v (I/O Port / MMIO write permitted by capability)
+--------------------------------------------------------------------------+
| VirtIO Hardware Device (PCI Bus Master)                                  |
|   Direct DMA Memory Cycle issued to Host DRAM Controller                 |
+--------------------------------------------------------------------------+
                         |
                         | [Bypasses CPU MMU / CR3 Page Tables]
                         v
+--------------------------------------------------------------------------+
| Physical DRAM @ 0x1000 (Kernel Root Page Table Overwritten!)              |
+--------------------------------------------------------------------------+
```

#### Remediation Architecture
Without hardware IOMMU support (which Janus does not currently support in Stage 3), **software alone cannot guarantee physical DMA isolation if raw MMIO/IOPort register access is delegated to Ring 3**.
Janus must adopt one of two explicit architectural postures:
1. **Option A (Trusted Kernel Bounce-Buffer Proxy - Recommended for Hard Isolation):** The driver does not possess raw bus-master MMIO capabilities. Instead, the driver submits I/O requests containing virtual memory buffers to the kernel; the kernel validates buffer ownership against the driver's CNode, populates physical descriptors using kernel-controlled bounce buffers, and dispatches the hardware command.
2. **Option B (Documented Threat Boundary - Pragmatic for Milestone 3):** Acknowledge that Milestone 3 achieves *Fault Isolation* and *Control-Flow Sandboxing* (driver crashes, null pointer dereferences, stack overflows, and CPU privilege escalation are trapped in Ring 3), but *hardware DMA attacks require an IOMMU (Milestone 4)*.

### 2.2 Asynchronous Notifications & Level-Triggered Interrupt Storms
#### The Design Claim
`MILESTONE_3_DESIGN.md` proposes an asynchronous `Notification` capability where hardware interrupts signal a bitmask in a notification object that wakes a waiting driver task.

#### Hardware Reality & Race Conditions
VirtIO legacy PCI interrupts (and standard PC-AT legacy IRQs) are **level-triggered** (`INTx` lines):
1. In a level-triggered interrupt scheme, the device asserts the PCI IRQ line and holds it asserted until the driver reads the device's Interrupt Status Register (e.g., reading VirtIO status offset `0x13` or PCI interrupt status).
2. If the kernel's Ring 0 interrupt handler acknowledges the local APIC / 8259 PIC (`EOI`) and posts a notification to the driver CNode, but **does not mask the hardware IRQ line at the PIC/IOAPIC**, the following catastrophe occurs:
   - Kernel executes `iretq` back to user space.
   - The device is still pulling the IRQ line LOW (asserted) because the driver has not run yet.
   - The CPU immediately re-enters the kernel interrupt handler before the driver can execute a single user-space instruction.
   - The system livelocks in an infinite **interrupt storm**.

#### Remediation Architecture
1. **Kernel Masking on Dispatch:** When a hardware IRQ fires, the kernel interrupt handler must immediately **mask (disable)** that specific IRQ line at the PIC / IOAPIC level before sending `EOI`.
2. **Explicit User-Space IRQ Acknowledgment:** The driver capability interface must provide an atomic syscall `SYS_IRQ_ACK(irq_cap)` which the driver invokes only after it has serviced the device registers and cleared the device interrupt condition.
3. The kernel unmasks the hardware IRQ line *only* upon receiving the valid `SYS_IRQ_ACK`.

### 2.3 The 32-Byte `CNodeSlot` Budget Assertion vs. Derivation Trees
#### The Existing Implementation Constraint
In `kernel/src/capability.rs`, line 78 enforces a strict compile-time assertion:
```rust
const _: () = assert!(core::mem::size_of::<CNode>() <= 4096);
```
With `CNODE_SLOTS = 128`, each `CNodeSlot` has a maximum allowable size of:
$$\text{Max Slot Size} = \frac{4096 \text{ bytes}}{128} = 32 \text{ bytes}$$

#### The Proposed Structure Defect
`MILESTONE_3_DESIGN.md` proposes expanding `CNodeSlot`:
```rust
pub struct CNodeSlot {
    pub capability: Option<Capability>,
    pub badge: Option<u64>,
    pub rights: Rights,
    pub parent: Option<usize>,      // 8 bytes
    pub first_child: Option<usize>, // 8 bytes
    pub next_sibling: Option<usize>,// 8 bytes
}
```
Calculating memory layout on x86_64:
- `Capability`: Tag (1 byte) + Variant Data (up to 16 bytes) + padding = 24 bytes
- `badge`: `Option<u64>` (16 bytes)
- `rights`: `Rights` (bitmask 1 byte + 7 bytes padding) = 8 bytes
- `parent`: `Option<usize>` = 16 bytes
- `first_child`: `Option<usize>` = 16 bytes
- `next_sibling`: `Option<usize>` = 16 bytes
- **Total Slot Size:** $\ge 96 \text{ bytes}$.
- **Resulting CNode Size:** $128 \times 96 = 12,288 \text{ bytes}$ (3 pages!).

This immediately **violates the compile-time static assertion** and breaks single-frame CNode allocations.

#### Remediation Architecture
To preserve the 4 KiB frame alignment and invariant, slot structures must use **compact 8-bit slot indices**:
- Since `CNODE_SLOTS = 128`, an index fits entirely in a `u8` (`0..127`), with `0xFF` representing `None`.
- `parent: u8`, `first_child: u8`, `next_sibling: u8` (Total: 3 bytes).
- Badge can be an unbadged `u64` where `0` denotes unbadged, or embedded inside `Capability::Endpoint`.
- Compact slot layout:
  ```rust
  #[repr(C)]
  pub struct CNodeSlot {
      pub capability: Capability, // 16 bytes (using compact enum)
      pub badge: u64,             // 8 bytes (0 = no badge)
      pub rights: u8,             // 1 byte
      pub parent: u8,             // 1 byte (0xFF = None)
      pub first_child: u8,        // 1 byte (0xFF = None)
      pub next_sibling: u8,       // 1 byte (0xFF = None)
      pub _reserved: [u8; 4],     // 4 bytes padding
  } // Total: exactly 32 bytes! 32 * 128 = 4096 bytes.
  ```

### 2.4 Driver Failure, Restart, and In-Flight Hardware State
#### The Design Claim
`MILESTONE_3_DESIGN.md` describes crash recovery:
> *"Fault Trapping: The kernel catches the fault, sets the driver state to Crashed, and sends a fault notification to the Device Manager. Devmgr calls `SYS_CAP_REVOKE` on all driver capabilities, reclaims its address space, and re-spawns the driver."*

#### Hardware Reality & Memory Corruption Bug
If a driver crashes (e.g., GPF, Page Fault) while a VirtIO block read or write is actively executing in hardware:
1. The physical device is actively writing incoming disk sectors to physical memory buffers.
2. If `devmgr` immediately revokes the driver's capabilities, frees the frames back to the physical frame allocator, and allocates those frames to another user task or kernel data structure, **the physical disk controller continues writing disk sectors into memory now owned by another process!**
3. Merely killing the driver task does **not** stop PCI bus-master DMA transfers.

#### Remediation Architecture
Hardware controllers must undergo an **explicit synchronous hardware reset** before any capability revocation or memory frame recycling:
1. The kernel or trusted `devmgr` must write `0` to the VirtIO Device Status Register (`RESET` condition) or clear Bit 2 (`Bus Master Enable`) of the PCI Command Register.
2. The reset sequence must poll or wait until the device acknowledges `DeviceStatus == 0` (indicating all internal queues and in-flight DMAs are terminated).
3. Only after the hardware controller is quiesced can the memory frames be safely reclaimed and re-allocated.

### 2.5 MMIO & I/O Port Range Conflict Protection
#### Vulnerability Analysis
The design proposes `IOPort { port: u16, count: u16 }` and `MmioFrame { paddr: u64, page_count: usize }`.
- If two different drivers (e.g., serial driver and virtio driver, or an unprivileged process) request overlapping I/O ports or MMIO regions, or if a driver derives a sub-capability covering ports `0x0020..0x0021` (8259 PIC registers) or `0x0070..0x0071` (CMOS/RTC), it could hijack kernel interrupt controllers.

#### Remediation Architecture
1. **Kernel Exclusion Range Check:** The capability minting engine must maintain a static exclusion table of reserved system ports and physical addresses:
   - System PIC (`0x20..0x21`, `0xA0..0xA1`)
   - PIT / Timer (`0x40..0x43`)
   - CMOS (`0x70..0x71`)
   - APIC / IOAPIC base addresses (`0xFEE0_0000`, `0xFEC0_0000`)
   - Local APIC MMIO ranges
2. **Mutual Exclusion:** Capability minting for `IOPort` and `MmioFrame` must be strictly exclusive. No two unrevoked capabilities in the system can claim overlapping physical port or memory ranges.

## 4. Critical Missing Prerequisites & Implementation Blockers

### 4.1 Blocker 1: The Virtual Memory Mapping Engine (Stage 3.0 Prerequisite)
In the existing codebase (`kernel/src/paging.rs`), physical frames can be allocated via `BootInfoFrameAllocator`, but there is **no subsystem to dynamically manipulate 4-level x86_64 page tables**:
- There is no function to take an arbitrary virtual address `vaddr`, locate or allocate intermediate page tables (`PML4 -> PDPT -> PD -> PT`), and map a physical frame `paddr` with specific user flags (`PRESENT | WRITABLE | USER_ACCESSIBLE | NO_EXECUTE`).
- There is no function to safely unmap a user page, flush the TLB (`invlpg`), and reclaim intermediate empty page tables.
- **Impact:** Attempting to implement `SYS_MAP_FRAME` in Stage 3.1 without first building this Virtual Memory Mapping Engine will result in an unworkable design.
- **Requirement:** A dedicated **Stage 3.0: Dynamic Virtual Memory Subsystem** must be introduced before any capability syscalls are written.

### 4.2 Blocker 2: User Process Runtime & ELF Loading Infrastructure
Currently, Janus launches user tasks by pointing RIP to pre-compiled static kernel function symbols (`test_user_process`, `test_user_process_b`) running inside the kernel code segment.
- A Ring 3 driver cannot be a static kernel function if it is to be truly isolated.
- It requires its own separate binary, separate memory segments (.text, .rodata, .data, .bss), and user stack.
- Without an ELF64 loader or raw user binary loader, user-space drivers cannot be independently deployed or restarted.

## 5. Architectural Decision Records (ADR Register)

### ADR-3.1: Capability Slot Memory Budget & Derivation Representation
- **Status:** **APPROVED WITH MODIFICATION**
- **Context:** `CNode` must not exceed 4096 bytes to preserve physical frame alignment. An array of 128 slots limits each slot to exactly 32 bytes.
- **Decision:**
  1. Embed rights as a single `u8` bitmask (`READ=1`, `WRITE=2`, `EXECUTE=4`, `GRANT=8`, `MAP=16`).
  2. Embed derivation tree links as 8-bit unsigned integers: `parent: u8`, `first_child: u8`, `next_sibling: u8`, where `0xFF` represents `None`.
  3. Badge is represented as a compact `u64` (8 bytes).
  4. Retain compile-time static assertion `assert!(size_of::<CNodeSlot>() == 32)`.

### ADR-3.2: DMA Isolation Strategy for Milestone 3
- **Status:** **ADOPTED WITH SCOPE RESTRICTION**
- **Context:** x86 PC architecture without an IOMMU allows bus-master PCI devices to bypass the MMU.
- **Decision:**
  1. For Milestone 3, Janus explicitly defines its security boundary: **Ring 3 CPU Isolation and Fault Resilience**. The system isolates CPU-level memory faults, panics, null-pointer dereferences, and privilege escalations.
  2. Full hardware-enforced DMA containment via IOMMU (Intel VT-d) is formally designated as **Milestone 4**.
  3. In Milestone 3, the VirtIO driver in Ring 3 will use `SYS_MAP_FRAME` to allocate contiguous physical DMA buffers. The kernel validates that the physical addresses programmed by the driver belong to its allocated set during VirtQueue registration.

### ADR-3.3: Level-Triggered PCI Interrupt Delivery Protocol
- **Status:** **APPROVED WITH MANDATORY MASKING**
- **Context:** Level-triggered interrupts cause infinite CPU interrupt storms if EOI is sent before the device clears its condition.
- **Decision:**
  1. When a hardware IRQ arrives at the kernel IDT, the kernel masks the IRQ at the PIC/IOAPIC, sets the bit in the registered `Notification` object, wakes any waiting driver task, and sends `EOI` to the local APIC.
  2. A new system call `SYS_IRQ_ACK(cap_idx)` is created.
  3. The driver calls `SYS_IRQ_ACK` after reading the device status register. The kernel verifies the caller holds the matching `Irq` capability with `WRITE` rights, and unmasks the hardware IRQ line.

### ADR-3.4: Synchronous Hardware Reset on Driver Crash
- **Status:** **APPROVED**
- **Context:** Reclaiming memory while a hardware controller is performing bus-master DMA corrupts memory.
- **Decision:**
  1. When a driver crashes or enters fault handling, the kernel or `devmgr` must immediately execute a device quiescence protocol:
     - Clear Bit 2 (`Bus Master Enable`) in the device's PCI Command register via port I/O `0xCF8/0xCFC`.
     - Write `0` to the VirtIO Device Status register.
  2. Memory frame reclamation is gated until the device reports status `0`.

## 6. Revised Implementation Roadmap

To avoid building upon missing foundations, the Milestone 3 implementation sequence is re-ordered into the following verified dependency pipeline:

```
[Stage 3.0: Dynamic VMM & Page Mapper] (Prerequisite)
                 │
                 ▼
[Stage 3.1: Compact Capability Engine & Slot Budget]
                 │
                 ▼
[Stage 3.2: Asynchronous Notifications & Masked IRQs]
                 │
                 ▼
[Stage 3.3: Dynamic Address Spaces & Syscall Layer]
                 │
                 ▼
[Stage 3.4: Ring 3 VirtIO Block Driver Extraction]
                 │
                 ▼
[Stage 3.5: Fault Trapping, Reset Protocol & Recovery]
```

### Stage 3.0 — Dynamic Virtual Memory Mapping Engine (PREREQUISITE)
- Implement `map_user_page(pml4, vaddr, paddr, flags)` in `kernel/src/paging.rs`.
- Implement dynamic 4-level page table allocation (`PDPT`, `PD`, `PT`) using `BootInfoFrameAllocator`.
- Implement `unmap_user_page(pml4, vaddr)` with TLB invalidation (`invlpg`).
- Implement per-task PML4 constructor copying higher-half kernel mappings (entries 256..512).

### Stage 3.1 — Compact Capability Engine & Rights Attenuation
- Refactor `CNodeSlot` to exactly 32 bytes using compact 8-bit derivation links.
- Implement `Rights` bitmask and capability attenuation logic (`SYS_CAP_DERIVE`).
- Implement recursive revocation (`SYS_CAP_REVOKE`) traversing derivation trees.

### Stage 3.2 — Asynchronous Notifications & Interrupt Dispatch
- Implement `Notification` capability with atomic 64-bit signaling bitmask.
- Implement kernel IDT $\to$ Notification dispatch.
- Implement hardware IRQ line masking and `SYS_IRQ_ACK` unmasking.

### Stage 3.3 — Dynamic Address Spaces & Capability Syscalls
- Implement `SYS_MAP_FRAME` and `SYS_UNMAP_FRAME` backed by Stage 3.0 mapper.
- Implement `SYS_NOTIFY_WAIT` and `SYS_NOTIFY_SIGNAL`.
- Validate user-pointer safety across all syscall boundaries using `copy_from_user` and `copy_to_user`.

### Stage 3.4 — Ring 3 VirtIO Block Driver Extraction
- Extract VirtIO block logic from `kernel/src/virtio.rs` into a standalone user-space driver.
- Grant driver `IOPort` capability for VirtIO legacy I/O range and `Irq` capability.
- Driver allocates DMA buffers via `SYS_MAP_FRAME` and exchanges block requests over IPC.

### Stage 3.5 — Fault Trapping, Quiescence & Driver Recovery
- Implement CPU exception routing (Page Fault, GPF) to supervisor notification.
- Implement synchronous PCI bus-master disable and VirtIO device reset.
- Implement clean driver respawning and address space reclamation.
